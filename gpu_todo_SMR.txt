It prints device identity, a --blocksize sweep, per-phase GPU timings, the candidates, and a pasteable block at the end. Add --cpu if you want a same-host CPU ratio — it's off by default because a CPU on an unfamiliar host isn't comparable to fitzroy's Xeon (three hosts have already differed by 2.4× per core), and it roughly doubles the runtime.

Rough cost on NGC6624: ~15 searches for the sweep plus one instrumented pass. At the 1080's 9.5 s that's ~2.5 min; on the faster cards, less. Both have plenty of memory headroom (1.29 GiB of amplitudes plus ≤0.8 GiB of workspace), and the guard will skip any blocksize that wouldn't fit rather than failing the run.

One caveat baked into the output

Per-phase timing serialises the GPU queue — a wall-clock timer around a CUDA launch measures the launch, so each phase needs a synchronise, which changes what's being measured. So the timers are opt-in (unlike the CPU's always-on ones), the sweep runs with them off, and the shares come from a separate pass with them on. On the 1080 the instrumented total reads 0.736 s against a clean 0.896 — ~20% inflation. The script says this in its own header: read the shares, take the total from the sweep.

What I'll be looking for

The transform is 38.5% here and should change most. §0.3 measured the Ada doing that stage 2.8× faster on its 40 MB L2, and the 2080 Super 2.75× on bandwidth — which would drop it to ~18% and make the boxcar the largest phase on both. That would flip what's worth optimising next.

The blocksize row is the other one. The 1080 wants the largest chunk; the Ada should want a much smaller one (its L2 optimum was 32768 in the standalone probe). If the search-level sweep agrees with the probe-level one, that's a nice confirmation the L2 story carries from isolated cuFFT calls into the real pipeline.

And it replaces the last projected column in the doc with a measurement — §0.46's ~4× for those cards is still an estimate carrying a projected metric phase, which §4.2 showed I was 26% optimistic about.
